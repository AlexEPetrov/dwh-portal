# Политика внутренней документации

Status: Accepted
Owner: platform
Last reviewed: 2026-09-11
Applies to: `openspec/**`, `rules/**`, `docs/**`, `AGENTS.md`

**Входной index:** [`docs/README.md`](README.md) — читать сначала.
Этот файл — полный reference. Агентам: не preload на каждую задачу; грузить
при создании/переносе/переклассификации документов или при сомнении в
размещении.

Этот документ определяет, **какие виды документации используются в проекте, где они хранятся и для чего нужны**.

Главная цель структуры — чтобы человек или ИИ-агент мог по расположению файла сразу понять его назначение.

---

## 1. Основная схема

В проекте используются следующие основные области:

```text
AGENTS.md
rules/
openspec/
docs/
```

Их назначение:

```text
AGENTS.md
= как агент должен работать с соответствующей частью репозитория

rules/
= правила выполнения изменений

openspec/
= текущее поведение системы и изменения этого поведения

docs/
= объяснения, решения, планы, методики и производная документация
```

Эти роли не следует смешивать.

---

## 2. `AGENTS.md` — инструкции для ИИ-агентов

Файлы `AGENTS.md` содержат инструкции для ИИ-агентов.

Корневой:

```text
AGENTS.md
```

задаёт общие правила работы с репозиторием.

Вложенные `AGENTS.md` уточняют правила для своей части дерева:

```text
backend/core-service/AGENTS.md
backend/calc-service/AGENTS.md
frontend/web/AGENTS.md
```

Агент загружает только применимую цепочку инструкций от корня до изменяемого пути.

`AGENTS.md` не является спецификацией поведения системы и не должен содержать подробное описание предметной области.

Файлы `AGENTS.md` пишутся на английском языке.

---

## 3. `rules/**` — правила выполнения изменений

```text
rules/
```

содержит правила, определяющие **как разрешено и требуется изменять систему**.

Здесь могут находиться:

```text
rules/
  README.md
  policy.yaml
  workflows/
```

Например:

- уровень самостоятельности агента;
- необходимость согласования человеком;
- правила изменения общих контрактов;
- обязательные проверки;
- порядок согласования изменений между сервисами;
- специальные процедуры для изменений повышенного риска.

`rules/**` отвечает на вопрос:

> Как это изменение должно быть выполнено?

Он не должен описывать функциональное поведение продукта.

# OpenSpec

## 4. `openspec/specs/**` — текущее поведение системы

```text
openspec/specs/**
```

содержит **текущее принятое описание поведения системы**.

Это основной источник ответа на вопрос:

> Что система должна делать сейчас?

Спецификации организуются по функциональным областям и возможностям системы.

Пример:

```text
openspec/specs/
├── balance/
│   ├── sources/
│   │   ├── excel/
│   │   │   └── spec.md
│   │   └── python/
│   │       └── spec.md
│   └── calculation/
│       └── spec.md
│
├── market-data/
│   ├── products/
│   │   └── spec.md
│   └── curves/
│       └── spec.md
│
└── valuation/
    ├── calculation/
    │   └── spec.md
    └── filters/
        └── spec.md
```

Структура `openspec/specs/**` отражает **функциональную структуру системы**, а не расположение классов и файлов исходного кода.

Например:

```text
balance/sources/excel
```

— это возможность системы, а не имя Python-модуля.

### Организация capabilities

В `openspec/specs/**` приветствуется иерархическая организация capabilities по функциональным областям.

Иерархия должна отражать функциональную структуру системы:

```text
крупная область
  → более узкая возможность
    → при необходимости подчинённая возможность
```

Не следует искусственно делать все capabilities плоскими, если между ними есть естественная функциональная иерархия.

При этом не нужно копировать структуру исходного кода. Иерархия capabilities описывает устройство продукта и его поведения, а не расположение модулей, классов или сервисов.

Полный путь capability внутри `openspec/specs/**` служит её устойчивым адресом, например:

```text
balance/sources/excel
market-data/products
valuation/filters
```

Глубину иерархии следует увеличивать только тогда, когда это делает функциональную структуру понятнее. Избыточная вложенность не приветствуется.

### Требования к читаемости

Каждая текущая спецификация должна начинаться с понятного заголовка и раздела `Purpose`.

Пример:

```md
# Excel-источник узла дерева Balance

## Purpose

Позволяет пользователю подключить диапазон из XLSX к базовой
или моделируемой позиции дерева Balance и использовать актуальные
числовые значения Excel в расчётах и при сохранении данных.

Capability определяет единое поведение Excel-источника при чтении,
расчёте, сохранении и обработке ошибок.

## Requirements
...
```

Раздел `Purpose` должен:

- объяснять назначение возможности простым человеческим языком;
- описывать, что она даёт пользователю или системе;
- объяснять, зачем она существует;
- не превращаться в перечень классов, функций и деталей реализации;
- обычно занимать от одного до трёх небольших абзацев.

Этот текст может напрямую использоваться при создании читаемой документации.

Дополнительные служебные поля `id`, `parent`, `level`, `status` и подобные сведения писать не требуется, если они однозначно определяются расположением файла.


Технические markup-заголовки должны быть на английском языке.
Описательный текст на русском языке.

## 5. Описание существующей системы

Для существующего проекта допускается постепенно описывать уже работающие возможности непосредственно в:

```text
openspec/specs/**
```

Для этого не требуется создавать искусственное изменение OpenSpec.

Например существующее поведение:

```text
Balance → Sources → Excel
```

может быть исследовано по:

- существующей документации;
- открытым интерфейсам;
- тестам;
- исходному коду;

после чего создаётся:

```text
openspec/specs/balance/sources/excel/spec.md
```

Исходный код при этом является доказательством фактической реализации, но не автоматически определяет правильное нормативное поведение.

Не требуется описывать весь старый проект сразу.

Спецификации следует добавлять постепенно, по функциональным областям и по мере практической необходимости.

## 6. `openspec/changes/**` — конкретные изменения

```text
openspec/changes/**
```

содержит конкретные предлагаемые или выполняемые изменения системы.

Например:

```text
openspec/changes/
  add-market-data-timeseries/
  fix-valuation-filter/
  reorganize-balance-services/
```

Изменение — это **единица работы**, а не постоянная функциональная область.

В зависимости от используемой схемы OpenSpec изменение может быть лёгким:

```text
proposal.md
tasks.md
```

или более подробным:

```text
proposal.md
specs/**
design.md
tasks.md
```

Не каждое изменение обязано создавать отдельную спецификацию поведения.

Для обычной разработки может использоваться облегчённая схема.

Для важных изменений поведения, общих контрактов или расчётной логики может использоваться полная схема со спецификациями.

После завершения изменение архивируется средствами OpenSpec.

# Документация

## 7. `docs/**` — внутренние материалы проекта

```text
docs/**
```

содержит материалы, которые помогают **понять систему, её устройство, историю и дальнейшее развитие**.

Текущая рекомендуемая структура:

```text
docs/
├── adr/
├── plans/
├── methodology/
├── technical/
├── product/
├── generated/
└── userguide/
```

При появлении реальной необходимости могут добавляться другие понятные разделы, например:

```text
docs/issues/
```

Но новые категории не следует создавать заранее без практической потребности.

## 8. `docs/adr/**` — архитектурные решения

```text
docs/adr/**
```

содержит архитектурно значимые решения.

ADR отвечает на вопрос:

> Почему система устроена именно так?

Рекомендуемая структура:

```text
docs/adr/
├── TEMPLATE.md      шаблон нового ADR (Nygard, English headings)
├── active/
└── superseded/
```

Формат — простой Nygard/MADR-lite. Заголовки секций **на английском**:

```text
## Status
## Context
## Decision
## Consequences
```

Статусы в `## Status`: `Proposed` | `Accepted` | `Superseded`
(допустимо `Draft` для черновиков). Текст тела может оставаться русским.
YAML frontmatter и `adr-capability-map.yaml` не используются.

Публикация на product-site — тегами в теле ADR (обычно под `## Status`):

```text
Product-publish: yes
Product-capabilities: valuation/service, reporting/valuation
Product-summary: optional one-liner
```

`PRODUCT-DOCS-SYNC` сам находит такие файлы в `docs/adr/active/**`.

### Новый ADR

1. Копировать `docs/adr/TEMPLATE.md` →
   `docs/adr/active/<domain>/<slug>.md` (для `platform/` — только
   cross-service; для `governance/` — устройство docs/process слоя).
2. Заполнить Status / Context / Decision / Consequences.
3. Поведение, следующее из решения, отразить в `openspec/specs/**` (или
   change), а не оставлять только в ADR.
4. Если ADR нужен на product-site — добавить теги `Product-publish` /
   `Product-capabilities` и прогнать `PRODUCT-DOCS-SYNC`.

### `docs/adr/active/**`

Содержит решения, которые продолжают действовать.

Например:

```text
docs/adr/active/
  risk-data-belongs-to-risk-domain.md
  python-rust-contract-uses-protobuf.md
```

Внутри `active/` решения сгруппированы по сервисам и доменам, к которым
относятся:

```text
docs/adr/active/
├── api/
├── calc-service/
├── core-service/
├── frontend/
├── management/
├── platform/      только cross-service решения
├── reporting/
├── risk/
├── valuation/
└── governance/    правила работы с документацией и изменениями
```

Каталог `governance/` отличается от остальных: он описывает не поведение
продукта, а устройство самого документационного и процессного слоя.

Реализация решения **не делает ADR устаревшим**.

ADR остаётся действующим, пока само архитектурное решение продолжает действовать.

### `docs/adr/superseded/**`

Содержит решения, которые были заменены более новыми.

Старые ADR не удаляются, потому что они объясняют историю развития архитектуры.

Если решение заменено, старый ADR должен явно ссылаться на новый и
**переезжает** из `docs/adr/active/**` в `docs/adr/superseded/**`. Статус
`Superseded` в тексте без смены каталога недопустим: путь — фильтр для
агентов.

### Связь ADR и OpenSpec

ADR и OpenSpec выполняют разные функции:

```text
ADR
= почему принято решение

OpenSpec spec
= какое поведение системы из этого следует
```

ADR не переносится в спецификацию после реализации.

Если архитектурное решение создаёт устойчивое обязательство поведения системы, это обязательство отдельно отражается в соответствующей спецификации OpenSpec.

## 9. `docs/plans/**` — крупные планы

```text
docs/plans/**
```

содержит планы, которые шире одного конкретного изменения OpenSpec.

Например:

```text
docs/plans/
  market-data-modernization.md
  liquidity-risk-rollout.md
  monorepo-migration.md
```

План может описывать:

- крупное направление развития;
- несколько этапов;
- несколько связанных изменений;
- зависимости между работами;
- последовательность перехода;
- риски;
- целевое состояние.

План отвечает на вопрос:

> Куда мы хотим прийти и как собираемся двигаться?

Одна небольшая функция обычно **не требует отдельного файла в `docs/plans/**`**.

Для неё достаточно:

```text
openspec/changes/<change>/
```

Один большой план может породить много изменений:

```text
docs/plans/market-data-modernization.md
    ↓
openspec/changes/add-product-tabs/
openspec/changes/add-timeseries/
openspec/changes/redesign-curves/
```

`docs/plans/**` является штатной частью документации и **не считается устаревшим каталогом**.

Конкретный план может иметь состояние, например:

```text
Idea
Proposed
Active
Completed
Superseded
Abandoned
```

Статус относится к конкретному документу, а не ко всему каталогу.

План не является источником текущего поведения системы.

Исполненный план не хранится бессрочно: он раскладывается в документы других
слоёв — решения в `docs/adr/active/**`, поведение через `openspec/changes/**` в
`openspec/specs/**` — после чего удаляется. Критерий и порядок описаны в
`docs/adr/active/governance/document-lifecycle.md`.

### `docs/plans/superseded/**`

Содержит вытесненные редакции документа, у которого есть более новая
действующая версия, когда сравнение версий сохраняет смысл. Пример — цепочка
`etrm_financial_model_v2..v9.1`, действующая редакция `v9.2` живёт в
`docs/methodology/`.

Завершённые планы сюда не складываются: по
`docs/adr/active/governance/document-lifecycle.md` они декомпозируются и
удаляются, а их историю хранит Git.

Каталог назван `superseded`, а не `archive`, потому что описывает то же
отношение, что и `docs/adr/superseded/**` — замену более новой редакцией. Имя
`archive` в репозитории закреплено за завершёнными единицами работы
(`openspec/changes/archive/**`).

## 10. `docs/methodology/**` — методики и обоснования

```text
docs/methodology/**
```

содержит методические материалы.

Например:

- статистические подходы;
- методы моделирования;
- расчёт показателей риска;
- методику формирования выборок;
- принципы оценки качества результатов;
- экономические и финансовые определения.

Этот раздел отвечает на вопрос:

> На какой методике основан расчёт или анализ?

Методика может объяснять математические и предметные основания поведения, но конкретные обязательства системы должны быть отражены в соответствующей спецификации OpenSpec.

## 11. `docs/technical/**` — технические объяснения и исследования

```text
docs/technical/**
```

содержит технические материалы, которые полезны для понимания реализации, но не являются спецификацией поведения или ADR.

Например:

- исследование производительности;
- сравнение библиотек;
- описание существующей технической схемы;
- результаты экспериментов;
- разбор сложного механизма;
- рекомендации по реализации;
- технические памятки.

Этот раздел отвечает на вопрос:

> Как это работает технически или что мы выяснили в ходе исследования?

Если исследование приводит к архитектурному решению, само решение следует оформить как ADR.

## 12. `docs/product/**` — продуктовый spine

```text
docs/product/**
```

содержит **компактный авторский продуктовый нарратив**: что это за продукт, для кого, какие сквозные сценарии и границы.

Он не заменяет:

* `openspec/specs/**` — нормативное поведение;
* `docs/userguide/**` — пошаговую in-app справку.

Правила:

* мало страниц; без MUST/SHALL и без дублей userguide;
* **язык продуктового сайта и spine — русский**; на end-user витрине английский сводится к минимуму (идентификаторы не переводятся);
* ссылки на справку — схемой `help:<id>`;
* curated ADR для внешней публикации — тег `Product-publish: yes` в теле
  ADR (`Product-capabilities` обязателен); sync ищет сам;
* привязка capability → help — через `docs/product/capability-help-map.yaml`.

Обоснование пайплайна: `docs/adr/active/governance/product-docs-pipeline.md`.
Инструкция по сборке: `docs/product/BUILD.adoc`.

## 13. `docs/generated/**` — автоматически созданная документация

```text
docs/generated/**
```

содержит документацию, автоматически построенную из существующих источников проекта.

Она может создаваться на основе:

```text
openspec/specs/**
+ openspec/capabilities.yaml
+ docs/product/**
+ отобранные ADR
```

`openspec/capabilities.yaml` — справочник направлений и features (включая заготовки
под будущие спеки). **Каждая** `openspec/specs/**/spec.md` должна быть листом
в этом справочнике с тем же path; спека «мимо» yaml недопустима. Лист без спеки
допустим. Подробнее — в шапке файла и в
`docs/adr/active/governance/product-docs-pipeline.md`.

Актуальный продуктовый AsciiDoc-компонент:

```text
docs/generated/product/          # Antora component (коммитится)
docs/generated/product-site/     # playbook-обвязка; HTML build/ не в Git
```

Пересборка:

```text
python3 infra/scripts/product_docs_sync.py --mode sync
```

Режим `--mode enrich` (AI) допускается только по явному запросу человека и не подменяет `sync`.
Русскоязычные narrative хранятся в `docs/generated/product-enrich/**` и вшиваются в компонент при сборке.
CLI не вызывает модель сам: текст пишет агент по запросу, затем `--mode enrich` пересобирает сайт.

Файлы в `docs/generated/**` помечены как производные (`DO NOT EDIT`) и не правятся вручную.

`docs/generated/**` является **производной документацией**, а не источником истины.

Направление обновления:

```text
спецификации + product spine + ADR с Product-publish: yes
                ↓
        docs/generated/**
```

Обратное автоматическое изменение спецификаций из `docs/generated/**` не допускается.

Static HTML, собранный из AsciiDoc (Antora и т.п.), в Git не хранится: это артефакт CI/публикации.

## 14. `docs/userguide/**` — руководство пользователя

```text
docs/userguide/**
```

содержит поддерживаемую вручную пользовательскую документацию приложения.

Этот каталог является одновременно источником встроенной справки веб-приложения: разделы регистрируются в `frontend/web/src/help/topics.ts` и импортируются оттуда через алиас `@userguide`. Поэтому:

- ссылки между разделами оформляются схемой `help:<id>`, а не путями к файлам;
- изображения размещаются в `docs/userguide/assets/**`;
- добавление документа требует регистрации раздела в реестре, иначе он не попадёт в приложение.

Правила авторства и состав каталога описаны в `docs/userguide/README.md`.

Это отдельный слой представления информации и не заменяет OpenSpec как источник текущего нормативного поведения. При расхождении с `openspec/specs/**`, `docs/methodology/**` или `docs/adr/**` приоритет за ними.

Ранее пользовательские и разработческие руководства велись как Sphinx-проект в `docs/source/**`. Проект удалён: актуальное пользовательское содержание перенесено в `docs/userguide/**`, архитектурные решения — в `docs/adr/**`, методологические материалы — в `docs/methodology/**`. Вместе с ним удалены обвязка сборки (`docs/build_docs.sh`, `docs/Makefile`, `docs/make.bat`, `docs/requirements.txt`), шаг сборки справки в `infra/scripts/_build_target.sh` и маршрут `/docs` в core-service, который отдавал сгенерированный HTML.

Продуктовый AsciiDoc-компонент для внешней/сгенерированной документации собирается в `docs/generated/product/**` командой `PRODUCT-DOCS-SYNC` и коммитится; static HTML из него — отдельно, без хранения в Git.

---

## 15. `docs/issues/**` — только при необходимости

Каталог:

```text
docs/issues/**
```

не создаётся заранее.

Если со временем появится реальная потребность хранить проблемы, технический долг или открытые вопросы непосредственно в Git, такой каталог может быть добавлен.

Его предполагаемая роль:

```text
docs/issues/**
= известные проблемы, долги и открытые вопросы
```

Если используется внешний учёт задач — GitHub Issues, GitLab Issues, Jira или другой инструмент — отдельный `docs/issues/**` обычно не требуется.

Не следует одновременно создавать несколько конкурирующих сущностей:

```text
issues/
backlog/
ideas/
todos/
```

без явной практической необходимости.

# Приоритет и достоверность

## 16. Инструкции, нормативное поведение и доказательства — разные вещи

Необходимо различать:

### Инструкции

Определяют, **как агент должен выполнять работу**:

```text
AGENTS.md
rules/**
```

### Нормативное поведение

Определяет, **как система должна работать**:

```text
openspec/specs/**
```

и утверждённые изменения в пределах текущего OpenSpec change.

### Архитектурные причины

Объясняют, **почему принято решение**:

```text
docs/adr/active/**
```

### Доказательства реализации

Показывают, **что фактически реализовано**:

- тесты;
- исходный код;
- опубликованные контракты;
- результаты выполнения.

Эти четыре категории не следует объединять в одну шкалу приоритетов.

---

## 17. Расхождение спецификации и реализации

Если:

```text
openspec/specs/**
```

говорит одно, а код или тесты показывают другое, нельзя автоматически считать правильным код.

Это может означать:

- ошибку реализации;
- устаревшую спецификацию;
- незавершённое изменение;
- незафиксированное изменение поведения.

Такое состояние должно быть явно рассмотрено как расхождение.

# Язык и стиль

## 18. Язык документов

Внутренняя документация проекта по умолчанию пишется **на русском языке**.

Исключение: структурные заголовки ADR (`## Status`, `## Context`,
`## Decision`, `## Consequences`) и значения статуса (`Proposed` /
`Accepted` / `Superseded`) — на английском (Nygard/MADR). Текст в секциях
может оставаться русским.

Исключение:

```text
AGENTS.md
```

пишутся на английском языке как инструкции для ИИ-агентов.

Для **продуктовой end-user витрины** (`docs/product/**`, `docs/generated/product/**`, enrich-слой) требование жёстче: английский сводится к минимуму.
Идентификаторы, API, enum и `help:<id>` не переводятся.

Не переводятся:

- имена файлов;
- имена классов и функций;
- имена полей;
- названия API;
- названия enum;
- точные значения констант;
- идентификаторы протоколов и форматов;
- общепринятые названия технологий.

Не следует без необходимости заменять простые русские слова английскими.

Например предпочтительно:

```text
текущее поведение
архитектурное решение
план
методика
проверка
ограничение
расхождение
```

вместо:

```text
current behavior
decision
roadmap
methodology
verification
constraint
drift
```

если английский термин не является частью исходного технического обозначения.

---

## 19. Сгенерированные файлы

Автоматически созданные файлы не редактируются вручную.

К ним относятся, например:

- OpenAPI;
- JSON Schema;
- сгенерированные клиенты;
- protobuf stubs;
- иные файлы, для которых существует исходный авторский файл и процедура генерации.

Изменять следует исходный файл, после чего выполнять зарегистрированную процедуру генерации.

# Итоговая карта

## 20. Куда что писать

```text
AGENTS.md
    инструкции для ИИ-агентов

rules/**
    правила выполнения и согласования изменений

openspec/specs/**
    как система должна работать сейчас

openspec/changes/**
    конкретные изменения системы

docs/adr/active/**
    действующие архитектурные решения и их причины

docs/adr/superseded/**
    заменённые архитектурные решения

docs/plans/**
    крупные планы, состоящие из нескольких изменений

docs/methodology/**
    методики расчёта, моделирования и анализа

docs/technical/**
    технические исследования и объяснения

docs/product/**
    компактный авторский продуктовый spine

docs/generated/**
    автоматически собранная производная документация (в т.ч. AsciiDoc-компонент)

docs/userguide/**
    руководство пользователя, оно же источник встроенной справки приложения

docs/issues/**
    при необходимости — проблемы и открытые вопросы
```

Кратко:

```text
Spec    — что система должна делать.
Change  — что конкретно меняем.
ADR     — почему архитектурно сделали именно так.
Plan    — куда идём в рамках крупной работы.
Rules   — как разрешено выполнять изменения.
Product — зачем продукт, кому и в каких сценариях.
Docs    — объясняют систему и сохраняют знания.
```

Новые виды документов и новые каталоги следует добавлять только тогда, когда для них появилась реальная повторяющаяся потребность.

**Простая структура предпочтительнее полной классификации всех возможных видов знаний.**
