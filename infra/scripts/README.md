# Infrastructure orchestration: shared local and CI entry points

## Ownership

The separation is by execution phase, not by file extension:

| Location | Responsibility |
|---|---|
| `infra/scripts/` | Producer orchestration: local/CI entry points, build/release assembly, checks and developer-only workflows |
| `infra/images/` | Dockerfiles, source/toolchain pins, image-specific build helpers and runtime files copied into an image |
| `infra/compose/` | Canonical deployment topology; no source build or package installation on the target |
| `infra/environments/<name>/` | Deployable payload input: portable lifecycle helpers, target configuration examples and target instructions |
| `.build/<name>/` | Generated transferable release; not authoring sources and not a second source tree |

An image-specific helper such as `build_dsh.py` belongs beside the Dockerfile
because it runs inside that builder stage. Cross-layer packaging/export does
not: the shared `package_release.py` lives here. Up/down belong in the target
payload because the same scripts run in checkout and after transfer to a server.

The desired workflow is build once, verify/package, then promote the same image
and deployment artifact. Target addresses and credentials are runtime inputs;
they should not cause recompilation or be baked into an image. A release carries
commit/image identity and checksums, not a promise of bit-for-bit reproducibility
or a signature/attestation that has not been implemented.

## Shared entry points

Run from repository root (the scripts resolve their checkout root themselves):

```sh
bash infra/scripts/build_env_portal_harness.sh
bash infra/scripts/build_env_test.sh
```

The same commands are the producer interface for a suitably provisioned CI job.
Both entries require Docker/BuildKit, Git, Bash and Python 3; application build
dependencies are handled by image recipes. Neither requires a host npm build.
Do not infer that the current GitLab job image supplies these tools. The existing
`.gitlab-ci.yml` still contains obsolete donor paths/commands and has not been
silently rewritten; adopting these entry points there requires CI reconciliation.

### One pipeline, two explicit profiles

Both thin entry points set their profile and delegate via `_build_target.sh` to
`build_release.py`, which uses the profile table and single exporter in
`package_release.py`. The old harness-specific exporter is a compatibility wrapper
only, not another pipeline. Defaults are repository-root `.build/test` and
`.build/portal-harness`. An optional first argument selects a different **new**
output directory (caller-relative when relative). Existing/partial paths and
dangling symlinks are refused before building; nothing is removed or overwritten.
No deployment starts during export.

| Profile | Image build composition | Release-specific payload |
|---|---|---|
| `test` | `infra/images/portal/build.sh`: sole Portal frontend/backend recipe | `dwh-portal-core-service.img`, base/dev Compose, portable up/down, image-derived `src` and `frontend-dist` for existing bind mounts |
| `portal-harness` | `infra/images/portal-harness/build.sh`: build that SAME Portal base, then DSH-only extension | `dwh-portal-dsh.img`, harness Compose, portable up/down/run-sql and public env example |

The shared Portal base is `134/dwh-portal-core-service:1.2`. Its recipe lives in
`infra/images/portal/`; `backend/core-service/build_image.sh` delegates there.
The old backend Dockerfile is a compatibility alias of the built base, not a
second application recipe. The extension starts from this Portal image and adds
source-pinned DSH/runtime files only. Portal owns MCP in both profiles, disabled
by ordinary application defaults; the harness launcher enables agreed settings.

Both releases contain:

The result contains:

- their image archive, preserving the image tag used by Compose;
- only their allowlisted canonical Compose and portable target files;
- `migrations/all.sql`, copied from a uniquely named never-started/network-none
  temporary container made from that image, not regenerated by a handwritten substitute;
- `commit-sh.txt`, `release.json`, `SHA256SUMS` and a completion/failure marker.

Real `.env` files/credentials are not automatically copied. Provision them securely
on the target; protect any artifact containing operational configuration. The
public example is not a prepared database, installed model or production secret.
Only the exporter-owned temporary container is removed. Partial export evidence
is retained; do not deploy a directory marked failed. Generated artifacts are
regenerated from sources, not fixed by hand.

### Test release compatibility and target configuration

The approved legacy test refactor removes destructive output cleanup, host source
cache deletion, host frontend copies and automatic real `.env` copies. Existing
`.build/test` output is preserved and must not be reused as a new output path.
The generated test release includes the image's `src` and `frontend-dist`, not
possibly stale checkout outputs. The existing Compose topology, ports, network,
project-name behavior and mount variable names are unchanged.

Provision a target `.env` securely or pass an explicit env-file path. Configure
`APP_LOC_SRC_HOST` to the bundled source tree (for example `./src` in a transferred
release), `APP_LOC_WHEELS_HOST` to a valid target path if needed, and all log,
storage and DWH mount paths for that target. Bind-mount paths are operational
configuration, not inferred from a copied workstation env file. Test has no
automatically generated credential/example derived from its real `.env`.
No production/test DB, firewall, network or real env setting is modified.

## Developer-only trial and checks

The memory demo is a developer workflow, not target payload:

```sh
bash infra/scripts/run_portal_harness_demo.sh
```

It retains the previous disposable Docker-run behavior and dedicated state volume.
The isolated image smoke remains in `infra/images/portal-harness/smoke.sh`; it is
image-specific validation. Target up/down and operator instructions are under
`infra/environments/portal-harness/`. Do not run demo and SQL deployment on the
same published ports simultaneously.

Dependency-free producer/portability fixtures:

```sh
python3 -B -m unittest discover -s infra/scripts/tests -v
```

Those fixtures use fake/mocked Docker and temporary directories, never real image
builds, exports, deployment, DB access or model requests. The agent's current
Docker prohibition remains in force for every producer entry point.

Source verification does not establish a working CI runner or a successful image
build/export/import/start. Those remain user-run checks; do not deploy a failed or
incomplete artifact. Portal availability on 5053 and actual DSH/Ollama session
behavior require fresh runtime evidence and are not claimed fixed by unification.

Unification source results: 32 image/runtime Python tests, 14 release/portability
tests and 12 Node fixtures passed, with one host-native TypeScript-stripping skip.
Registered shell syntax checks passed. No Docker or live DB/model command ran.

The harness Compose definition now uses `docker-compose-portal-harness.yml` in
checkout and newly exported releases. The format-only conversion passed 33
image/runtime source tests and all 14 release/portability tests; a normalized
configuration checksum confirms identical values to the former JSON definition.
Image-source tests use the existing host PyYAML parser; the producer/portability
suite itself remains dependency-free. No Docker execution is needed for either.
